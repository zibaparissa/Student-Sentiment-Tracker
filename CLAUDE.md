# Spark! daily check-in — project notes

A one-page web app for a classroom mood check-in. Students scan a QR code on the projected
dashboard, submit an anonymous check-in from their phone, and the same page aggregates the
room's answers live.

Built for BU Spark!'s FA26 XC475 practicum. Owner: Ziba Cranmer.

**Live:** https://student-sentiment-tracker.web.app
**Firebase project:** `student-sentiment-tracker` (owned by a personal Google account —
BU Workspace blocks project creation)

## Repo shape

```
spark-checkin/
├── firebase.json          # generated by `firebase init`
├── .firebaserc
├── firestore.rules        # source of truth for the data schema — see below
├── firestore.indexes.json # empty; the app needs no composite indexes
└── public/
    └── index.html         # the entire application, ~1180 lines
```

`public/index.html` is the whole thing: markup, CSS, application JS, and an inlined copy of
the `qrcode-generator` library (MIT, Kazuhiko Arase) starting around line 329. There is no
build step, no bundler, no npm dependencies at runtime. Firebase SDK v10.12.2 is loaded at
runtime via dynamic `import()` from gstatic.

**Do not introduce a build step or split this into modules.** Single-file is a deliberate
constraint: the owner is not a full-time developer, deploys by hand, and needs to be able
to open one file and read it. A toolchain here would rot within a semester.

## How it works

Two screens behind a hash router (`route()`, ~line 1107):

- `/` — the dashboard, projected in class
- `/#/checkin` — the student form, reached by QR

The QR code is generated client-side from `location.origin + location.pathname + "#/checkin"`,
so it always points at wherever the page is served. Nothing to configure, but it also means
**changing the hosting URL invalidates every printed QR code**.

### Data flow

Anonymous Firebase Auth gives each device a stable `uid`. Document IDs are `{day}_{uid}`,
which is what enforces one check-in per device per day and lets a student replace their own
answer (a second submit overwrites) without being able to touch anyone else's.

The dashboard subscribes to a 120-day window with `onSnapshot` and aggregates entirely in
the browser. There is no server, no Cloud Function, no admin SDK.

### Document schema

```
checkins/{YYYY-MM-DD}_{uid}
  day      "2026-09-21"      local date string; all grouping keys off this
  course   "FA26 XC475"      absent on entries written before 2026-09-22
  team     "CENSE"
  mood     4                 int 1–5, matching SCALE
  words    ["focused","tired","ready"]
  uid      "abc123"          anonymous auth uid
  ts       <serverTimestamp>
```

`firestore.rules` enforces this with `hasOnly`, so **adding a field to an entry requires
editing the rules and publishing them before deploying the page**, or every write fails.
This has bitten us once already. The rules also forbid delete entirely and allow read to
any signed-in user.

## The config block (lines ~345–390)

Everything the owner is expected to edit lives here, in one block near the top.

```js
const COURSES = {
  "FA26 XC475": ["Arcadia", "CENSE", "ABUJA", "Sapling", "VoiceGuard", "Instructors"]
};
const LEGACY_COURSE = "FA26 XC475";   // what pre-class-picker entries belong to
const TEAM_ALIASES = { "nicole": "VoiceGuard", "instruction team": "Instructors", ... };
```

- One class in `COURSES` → students never see a class question, dashboard selector hidden.
  Two or more → both appear automatically.
- `TEAM_ALIASES` keys are lowercase, whitespace-collapsed. `canonTeam()` checks aliases
  first, then case-insensitive roster match, then falls through to the raw string.
- Team names are expected to change mid-semester. Renaming = change `COURSES`, add the old
  spelling to `TEAM_ALIASES`.

`SETTINGS` above it: `minToShow: 3` (privacy floor), `cloudMax: 45`, `collection: "checkins"`.

## Design decisions worth not re-litigating

**No names, ever.** An earlier version had an optional name field with an anonymity
checkbox. It was removed because the dashboard aggregates client-side, which means any
student with devtools can read the whole collection — "not displayed" is not "not readable."
The rules now make an identifying field impossible to store, not merely unasked-for. If
names are ever genuinely needed, the correct fix is a Cloud Function writing per-day summary
docs and rules denying client reads on `checkins` — not re-adding the field.

**Team entry is buttons, not free text.** Week one of real use produced 17 team names for
6 teams (`cense`/`Cense`/`CENSE`, six variants of "Instructors"). The dashboard was useless.
Free text is not coming back.

**Everything is indexed by session, not calendar date.** A "session" is a day that has
check-ins (`sessionDays()`, ~line 668). The class meets twice a week; a calendar x-axis drew
a chart that was 5/7 empty with the line crushed into one corner. All windows are expressed
in sessions — "last 5", "last 10", "all".

**The dashboard falls back to the most recent session.** `focusDay()` returns today if today
has data, else the latest session. Opening the page at 9am used to show an empty state with
55 check-ins sitting in the database.

**Sentiment is a word list, not a model** (`LEX`, ~line 408, roughly 200 entries scored −3..+3).
A client-side page cannot hold an API key. Unmatched words appear in the cloud but are
excluded from the sentiment figure rather than guessed at. Extending it means adding keys to
`LEX`. If real NLP is ever wanted, it belongs in the same Cloud Function as the aggregation.

**The mood ramp is darker than Spark! brand colors.** `MOOD_COLOR` (line 404) runs
`#B3350F → #D2662F → #77857E → #2A8478 → #00645C`. The brand orange/teal pair measured
1.4–2.6:1 against the `#E3EEE5` page background — invisible on a projector. Every step now
clears 3:1, and each bar carries a face, label and count so the scale never depends on color
alone. **Do not "restore brand colors" on the data marks.** Brand teal `#00A99E` is still
used for UI chrome.

## Deploying

Rules first, always:

1. Paste `firestore.rules` into the Firebase console → Firestore → Rules → Publish
2. `firebase deploy` from the project root

Deploying a page that writes a field the published rules don't allow fails silently from the
student's side — they see "That didn't send."

Verification after any deploy: hard-refresh (Cmd+Shift+R — Hosting caches hard), confirm the
header dot reads "live", confirm the By-team section shows 6 rows not 17, then submit one real
check-in from a phone. The check-in is the only thing that proves the rules accepted the write.

**Status as of 2026-10-09: the rebuilt version (class picker, session-indexed charts, team
canonicalization, darker ramp) has NOT been deployed yet.** The live site is still the
original build. If the By-team section shows ~17 cards, you're looking at the old one.

## Testing

There is no test suite. What has been used:

- **jsdom smoke test** — load the file with `runScripts:"dangerously"`, stub
  `HTMLCanvasElement.getContext` and `clientWidth`, let the demo store seed, then assert on
  rendered DOM and drive a submit. Catches render crashes and validation regressions.
- **Playwright screenshots** against a copy with `FIREBASE_CONFIG` blanked (which flips the
  app into its built-in demo store). Chromium at `/opt/pw-browsers/`. Layout bugs — overlap,
  wrap, contrast — only show up visually.
- To test team canonicalization, seed the demo store's `NAMES` array with the messy
  spellings and assert the dashboard collapses them to 6 rows.

The demo store (`demoStore()`, ~line 547) activates whenever `FIREBASE_CONFIG.apiKey` is
missing. It generates a plausible semester in `localStorage`. Use it for any UI work — don't
write test data into the real Firestore.

## Known limits and open items

- **Any signed-in user can read the whole collection.** Inherent to client-side aggregation.
  Acceptable because entries carry no identity. Revisit only if that changes.
- **Hosting is on a personal Google account.** BU blocks Workspace project creation. The BU
  account should be added as an Owner under Project settings → Users and permissions for
  continuity; unclear whether that's been done.
- **No export.** Getting data out means the Firebase console or a one-off script. A CSV
  download button on the dashboard would be a reasonable small addition.
- **Term rollover is untested.** Adding a second entry to `COURSES` should just work —
  the picker and dashboard selector both appear automatically — but it has never run with
  two live classes.
- Signal to watch is the per-team delta, not absolute averages. Teams cluster 3.2–4.5 on a
  1–5 scale; a team dropping half a point is the interesting event.

## Conventions

- Prose in the UI, not labels: "No check-ins yet today", not "NO DATA".
- Empty states say what will fill them and why it's empty.
- Student-facing copy stays short enough to read on a phone in a classroom.
- `aria-pressed` on every toggle; focus is visible; `prefers-reduced-motion` respected.
- The page must render standalone from `file://` with no network for the demo store to work.
